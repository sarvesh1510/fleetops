# FleetOps India

**Fleet dispatch and operations console for Mumbai MMR and Delhi NCR.**

FleetOps runs a simulated delivery fleet (78 vehicles: 44 in Mumbai MMR, 34 in Delhi NCR), dispatches pending orders to vehicles, reacts to breakdowns and traffic surges, and shows all of it live in a web dashboard.

Everything is simulated: vehicles, telemetry, orders and incidents are generated by the in-process simulation engine. The ML models are trained at startup on synthetic data (see [Machine learning](#machine-learning)), so their metrics describe the synthetic world, not real-world accuracy.

---

## What it does

| Area | Behaviour |
|---|---|
| **Simulation** | 2-second ticks, 1x/2x/5x/10x speed, pause/resume. Vehicles drive pickup → delivery along real roads (OSRM routing, straight-line fallback if unreachable), load/unload, refuel when low, and get slowed by regional traffic. |
| **Dispatch** | New orders, breakdowns and a 30 s schedule trigger a dispatch run. Vehicles are only matched inside their own region and must satisfy capacity, cold-chain and fuel-range constraints. |
| **Incidents** | A breakdown creates an incident with a timeline, reassigns the vehicle's active order through the dispatcher, and can be resolved with notes. Traffic surges create (and later expire) regional incidents. |
| **Orders** | Create orders (cross-region and out-of-region coordinates are rejected), follow status transitions, see assignment and ETA. |
| **Analytics** | On-time rate, ETA accuracy, delivery volume per hour (IST), cost per delivery. Values are computed from delivered orders; where there is no data yet they are shown as empty, not invented. |
| **Predictions** | The ETA model quotes the ETA of every assigned order; the page compares it with simple formulas on held-out trips and on real simulated deliveries (predicted vs actual). Also a what-if ETA estimator, demand forecast per zone/hour, telemetry anomaly check (Isolation Forest). |
| **Auth** | JWT + bcrypt, four roles: Admin, Ops Manager, Dispatcher, Viewer. WebSocket requires the token (`?token=`). |

## Quick start

### Docker Compose

```bash
cp .env.example .env
docker compose up
```

- Frontend: http://localhost:3000
- API docs: http://localhost:8000/api/docs
- MongoDB: localhost:27017

### Local development

Prerequisites: Python 3.11+, Node 20+, MongoDB 7+ running locally (or an Atlas URI).

```bash
# Backend
cd backend
python -m venv venv
venv\Scripts\activate          # Windows;  source venv/bin/activate elsewhere
pip install -r requirements.txt
cp ../.env.example .env        # set MONGODB_URI if Mongo is not on localhost:27017
uvicorn app.main:app --port 8000

# Frontend (new terminal)
cd frontend
npm install --legacy-peer-deps
npm run dev                    # http://localhost:5173, proxies /api and /ws to :8000
```

To point the dev server at a backend on another port: `API_TARGET=http://localhost:8001 npm run dev`.

On first start the database is seeded with users, the fleet and 320 historical delivered orders (so analytics have something to show). No incidents or dispatch runs are pre-seeded; they appear as the simulation produces them. If the stored schema version differs from the code, the collections are rebuilt on startup.

## Using the demo

Open the **Simulation** menu (top right of the Dashboard):

| Control | Effect |
|---|---|
| Pause / Resume | Freeze or resume all vehicles |
| Speed | 1x / 2x / 5x / 10x |
| Traffic surge | Slow all vehicles in the chosen region (Mumbai MMR or Delhi NCR); the surge expires on its own |
| Vehicle breakdown | Break down a random en-route vehicle (returns an error if none is en route) |
| New order | Inject a random order |

Suggested flow: watch the Dashboard map → trigger a breakdown → open **Incidents** to read the timeline and the reassignment → open **Dispatch** to see the run it triggered, compared with a baseline → open **Predictions** to try the ETA estimator.

## Architecture

```
Browser (React + Vite)
   │ REST + WebSocket (/ws/fleet?token=…)
   ▼
FastAPI
  ├── routers: auth, vehicles, orders, incidents, optimization (+analytics, predictions), simulation
  ├── SimulationEngine   in-process asyncio loop, 2 s ticks
  ├── OptimizationEngine dispatch (scipy Hungarian assignment)
  ├── MLEngine           trained in a background task at startup
  └── WebSocket broadcaster
   ▼
MongoDB (users, vehicles, orders, incidents, optimization_runs, telemetry)
```

Design decisions are recorded in [`docs/decisions.md`](docs/decisions.md).

### Dispatch logic

1. Every (order, vehicle) pair is scored. Hard constraints (same operating region, capacity, cold chain, fuel range) rule a pair out; soft factors (pickup distance, vehicle health, deadline pressure) shape the score.
2. The assignment that minimises total pickup distance, with a priority bonus so critical orders win scarce vehicles, is found with the Hungarian algorithm (`scipy.optimize.linear_sum_assignment`).
3. As a baseline we compute what a naive dispatcher would do: first-come-first-served, each order taking the nearest feasible vehicle. The reported improvement is the real difference between the two plans in pickup distance and time, and is frequently 0% when there is little choice.
4. Runs that assigned nothing and were not requested manually are not stored.

It is a one-to-one assignment solver, not a multi-stop route optimiser (no VRP).

### Machine learning

| Model | Algorithm | Notes |
|---|---|---|
| ETA | XGBoost regressor with monotone constraints, inside the ETA formula | The simple formula is `distance / (free-flow speed / congestion) + handling time`. Its weak spot is `congestion`: it uses the reading at assignment time. XGBoost predicts the congestion the trip will actually meet (e.g. rush hour starting mid-trip) from congestion now, typical congestion over the trip window, and the time of day; that prediction goes into the same formula. More traffic never lowers the estimate. Used for every order the dispatcher assigns. The `speed_kmh` field of `/predictions/eta` is the free-flow speed. |
| Demand | Gradient boosting | Orders per zone per hour |
| Anomaly | Isolation Forest | Speed, fuel rate, stop duration, route deviation, engine temperature |

MAE/RMSE shown in the UI come from a held-out split of the synthetic data. Endpoints return `503` while the models are still training.

**ETA model in the system.** When the dispatcher assigns an order, `SimulationEngine.estimate_order_eta` computes three estimates and stores them on the order: the ML model's (this is the quoted ETA once the model has trained), the simple formula's, and a fixed-speed guess (25 km/h, no traffic). When the order is delivered, the real elapsed time is stored next to them. `GET /predictions/eta-evaluation` scores all three against (a) held-out synthetic trips and (b) real delivered orders, and the Predictions page shows both, plus a predicted-vs-actual scatter. While driving, the live ETA countdown still uses the remaining road distance and current traffic.

**Reading the results honestly.** The ETA model is trained on trips generated with the simulator's own rules (`backend/app/simulation/profile.py`), so it learns the simulated world, not real roads. Its gain over the simple formula comes from trips that cross a rush-hour boundary; in calm traffic the two are about equal. Manually triggered traffic surges are not modelled, so all estimates are off during one. The speed multiplier changes how much traffic shifts during a trip; the model takes it into account.

## API

Interactive docs at `/api/docs`. All routes below are under `/api/v1` except health and the WebSocket.

```
POST /auth/login            GET  /auth/me             POST /auth/logout

GET  /vehicles              GET  /vehicles/stats      GET  /vehicles/{id}
GET  /orders                POST /orders              GET  /orders/stats       GET /orders/{id}
GET  /incidents             GET  /incidents/stats     GET  /incidents/{id}     POST /incidents/{id}/resolve

POST /optimization/run      GET  /optimization/runs   GET  /optimization/runs/{id}   GET /optimization/stats

GET  /analytics/overview    GET  /analytics/deliveries-per-hour    GET /analytics/eta-performance

GET  /predictions/status    POST /predictions/eta     GET  /predictions/eta-evaluation
GET  /predictions/demand    POST /predictions/anomaly

GET  /simulation/status     POST /simulation/start|pause|resume|speed
POST /simulation/trigger/traffic|breakdown|order

GET  /health                GET  /ready               WS   /ws/fleet?token=<jwt>
```

WebSocket events: `fleet.snapshot`, `vehicle.updated`, `vehicle.status_changed`, `vehicle.rerouted`, `order.created`, `order.updated`, `order.assigned`, `delivery.completed`, `route.updated`, `incident.created`, `incident.updated`, `incident.resolved`, `optimization.started`, `optimization.completed`, `alert.created`, `simulation.status`.

Message shape: `{ "event": "...", "timestamp": "...", "data": { ... } }`. Timestamps are UTC.

## Deployment notes

- The simulation runs inside the API process, so run a single backend instance.
- Use MongoDB Atlas or any MongoDB 7+ and set `MONGODB_URI`.
- Frontend: `cd frontend && npm run build`, then serve `dist/` from any static host and proxy `/api` and `/ws` to the backend.
